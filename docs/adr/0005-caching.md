# 5. Кеширование списка доступных гаражей на 5 секунд

- **Статус**: принято
- **Дата**: 2026-10-15
- **Участники**: вся команда

## Контекст

Функция поиска (`FR-01`) является самой частой операцией в системе. Каждый раз, когда водитель двигает карту, отправляется запрос к базе данных на поиск гаражей с учетом геолокации и проверки пересечения временных интервалов. Это тяжелый SQL-запрос с соединением таблиц (JOIN). 
Требование `NFR-01` гласит, что 95% таких запросов должны выполняться быстрее 300 мс. При росте нагрузки (много водителей онлайн) база данных может не справиться.

## Движущие факторы

- `NFR-01`: Поиск < 300 мс.
- `FR-01`: Пользователь должен видеть актуальную информацию о свободных местах.
- `C-04`: Мы не хотим усложнять инфраструктуру.

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| **Кеш в оперативной памяти (TTL 5 сек)** | Просто реализовать (встроенные средства Python), снижает нагрузку на БД, ускоряет ответ | Данные могут быть неактуальны до 5 секунд, при перезапуске сервера кеш сбрасывается |
| Без кеша (прямой запрос к БД) | Всегда актуальные данные, проще код | Высокая нагрузка на БД, риск не уложиться в `NFR-01` при пиковой нагрузке |
| Redis (внешний кеш) | Надежно, разделяется между серверами | Дополнительный контейнер в Docker, больше сложности для команды из 2 человек |

## Решение

Использовать **in-memory кеширование** (например, через библиотеку `cachetools` в Python) с временем жизни записи (TTL) **5 секунд**.

Ключом кеша будет комбинация параметров поиска (координаты, дата). При создании новой брони кеш для этой области будет инвалидироваться (сбрасываться) вручную.

**Определяющий довод** — баланс между производительностью и сложностью. 5 секунд — это незаметная задержка для пользователя, но она отсекает 90% повторных запросов к БД (если пользователь просто крутит карту туда-сюда).

## Последствия

**Положительные.** 
Резкое снижение нагрузки на PostgreSQL. Гарантированное выполнение `NFR-01` при пиковых нагрузках.

**Отрицательные.** 
Появляется "eventual consistency" (согласованность в конечном счете). Водитель может увидеть на карте гараж как свободный, нажать "Забронировать", и получить ошибку (409 Conflict), потому что за эти 5 секунд его уже кто-то занял. Однако, даже без кеша эта ситуация возможна (человек думает 10 секунд перед нажатием кнопки).

**Что пересмотрит решение.** 
Если количество серверов (инстансов) вырастет больше одного, in-memory кеш перестанет работать корректно (разные серверы будут иметь разные данные). В этом случае мы перейдем на Redis.
